## Rime frontend (Weasel/Arify) Candidate selection & Preedit persistence
- **Problem 1**: `preedit` persisted after Space (aka. `上屏时不应该把preedit也上屏`). This was because `get_result_string()` persistently read `GCS_RESULTSTR` directly. `GCS_RESULTSTR` lives until the next composition, so `GetCommit` kept returning the same commit word. Arify/weasel would repeatedly insert the commit AND preedit during typing.
- **Fix 1:** Used `trans_msgs` (TRANSMSG structs) from `ImeToAsciiEx` to accurately track `WM_IME_COMPOSITION` with `GCS_RESULTSTR` flag. Only when this flag is present do we read the result and set `session.pending_commit`. `GetCommit` uses `.take()` to consume it exactly once.
- **Problem 2**: "上屏应该上实际上屏词而不是候选词" (The hint/candidate word was committed instead of the actual word). This occurred because Weasel doesn't always send numbers via `process_key`; it uses `rime_api->select_candidate_on_current_page(N)`. Since the gRPC proxy didn't override this, Weasel couldn't tell QQPinyin to select it! Consequently, Weasel fell back to an internal mechanism that literally extracted the raw candidate text (including hints) and committed it manually while leaving QQPinyin's IMM context completely untouched.
- **Fix 2:** Overrode `select_candidate_on_current_page` in `grpc_proxy_module.cc`, created `SelectCandidate` proto RPC, and implemented it in the host. The Win32 Host triggers `ImmNotifyIME(session.himc, NI_SELECTCANDIDATESTR, 0, index)`. QQPinyin successfully processes this notification and places the raw, correct word into `GCS_RESULTSTR`, seamlessly consumed by the Fix 1 logic returning the exact phrase to Weasel via `GetCommit`.
